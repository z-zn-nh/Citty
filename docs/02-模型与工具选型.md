## 1. 一句话选型结论

| 环节 | 默认选型（本地实时） | 高质量档（离线/云端） | 备选 |
|---|---|---|---|
| 音频捕获 | WASAPI loopback（`soundcard` / `pyaudiowpatch`） | — | 浏览器 `tabCapture`（仅网页） |
| VAD/断句 | Silero VAD + 静音边界 commit | — | FunASR VAD（中文） |
| ASR（流式） | `nvidia/nemotron-3.5-asr-streaming-0.6b`（chunk 320ms） | `whisper-large-v3-turbo`（faster-whisper）批处理 | `microsoft/VibeVoice-ASR-Streaming-1.5B`（要说话人归属时）、`FunASR`（中文）、`WhisperLiveKit` 作为框架 |
| MT | **Index-Translate-2B**（FP8/GGUF，本地） | **Index-Translate-9B / 免费 35B-A3B API**、`tencent/Hy-MT2-7B/30B-A3B` | `google/translategemma-4b/12b`（55 语种）、`ByteDance-Seed/Seed-X-*` |
| 翻译上下文修正 | 同一 MT 模型，带前 3~5 句 + 术语表 | Index-NativeLong（整篇） | — |
| 时长/音节控制 | （P2）Index-Homura | Index-Homura-9B | 自研变速对齐 |
| TTS | （P2）`IndexTeam/IndexTTS-2.5` | `Index-Echo-S2ST-9B`（端到端配音） | `Fun-CosyVoice3-0.5B`、`F5-TTS`、`GPT-SoVITS`、云端 TTS |
| 人声分离 | （P2）`demucs` two-stem | UVR/MDX 系 | 实时只做 ducking |
| 路由/分类 | 2B 级小模型 + prompt 分类（先埋点） | **`autotrust/JEV-9B` / `JEV-27B-VL`**（`/v1/decide`） | `GEV-26B-Decide`（61ms，但 26B 太大） |
| 字幕渲染 | 透明置顶窗 / 扩展 overlay（三模式） | — | OBS 文本源（推流场景） |

## 2. 翻译模型详细对比

### 2.1 三个候选的硬指标

| 项 | Index-Translate（B 站） | Hy-MT2（腾讯） | TranslateGemma（Google） |
|---|---|---|---|
| 发布 | 2026-09-30 | 2026-05-21（上一代 2025-12 / 2025-09） | 2026-01（4B/12B/27B） |
| 规模 | 2B / 9B / 35B-A3B(prev) | 1.8B / 7B / 30B-A3B | 4B / 12B / 27B |
| 语种 | **150** | 33（含藏维蒙哈等） | 55 |
| 许可 | Apache-2.0 | Apache-2.0 | 需核对（Gemma 系自定义条款） |
| 量化 | GGUF / FP8(W8A8) / NVFP4(W4A4) | GGUF（含 2bit/1.25bit，1.8B→440MB）/ FP8 | GGUF 社区版 |
| 公网免费 API | **有**（`index-translate.bilibili.com/v1`，OpenAI 兼容，35B-A3B） | 无（官方走 AI Studio） | 无 |
| 特色 | 术语/格式硬约束、文风软约束、**字幕翻译与 MEME 专项评测**、同家族 S2TT/S2ST/Homura/NativeLong | domain-specific 与 business 场景评测强、端侧极低比特量化、**WMT26 视频字幕任务**赞助 | 通用多语，架构基于 Gemma 3 |
| 参考延迟 | 2B 本地：单句 ~80~250ms（估计） | 1.8B 本地更快；7B 明显更慢 | 4B 起 |

> 上面"参考延迟"是本机档位的**估算**，必须实测后再写进文档。

**怎么用这张表**：
- 它说明"专用翻译模型在小尺寸上确实打平/超过通用大模型"，这支持你选专用 MT 而不是"什么都用通用 LLM"。
- 它**不能直接证明**"科技类要选腾讯"——表里没有分领域结果，而且是 B 站自己的评测集。你自己的 A/B 是唯一证据。

### 2.3 关于"腾讯更适合科技类"这个假设

Hy-MT2 官方确实做了 **domain-specific** 维度的评测（官方卡片原文：general / real-world business / **domain-specific** / instruction-following），并且把 IFMTBench 开源了——**这为你的假设提供了动机，但不构成证据**。要验证，用第 5 节的方案。

一个更容易拿收益的中间路线：
- **术语表 + 领域 prompt 走"硬约束"**（Index-Translate 支持 `--glossary` 与 `--hard`；Hy-MT2 支持 33 语种指令）。
- 这两个动作的成本接近 0，收益通常比"换模型"更大更稳（尤其是科技类里的专名、缩写、版本号）。
- 把"换模型"当成第二层优化，用数据说话。

## 3. ASR 选型

| 模型/框架 | 规模 | 流式 | 语种 | 延迟档 | 许可 | 备注 |
|---|---|---|---|---|---|---|
| `nvidia/nemotron-3.5-asr-streaming-0.6b` | 0.6B | ✅ cache-aware | 36 locale（含 zh-CN、en） | chunk 80/160/320/560/1120ms | OpenMDW-1.1 | 主推；带标点大小写；FLEURS zh-CN WER ≈19~21% |
| `microsoft/VibeVoice-ASR-Streaming-1.5B` | 1.5B | ✅ | 10（中英日韩法德意西葡俄） | 未标注 | MIT | 唯一强调**流式说话人归属 + 热词**的 |
| `openai/whisper-large-v3-turbo`（faster-whisper/CT2） | 0.8B | 半流式（需 SimulStreaming/LocalAgreement） | ~99 | 1~3s | MIT | 准但慢，适合离线/修正 pass |
| `modelscope/FunASR`（Paraformer/SenseVoice） | 0.2~1B | ✅ | 中文为主 + 部分 | 低 | Apache/MIT 视模型 | 中文场景质量稳；有 GGML 纯 C++ 版 |
| `QuentinFuxa/WhisperLiveKit` | 框架（11.1k★） | ✅ | 取决于后端 | 取决于后端 | Apache-2.0 | 直接当引擎用：VAD、Sortformer 说话人分离、WebSocket、**内置同传（NLLB 200 语种 / AlignAtt4LLM）** |

**建议**：第一版直接用 WhisperLiveKit 当 ASR 服务（省掉 VAD/断句/接口一堆工程），后端先选 faster-whisper 把链路跑通，再切 nemotron-3.5 拿低延迟。

**中文专项**：中文 ASR 的槽点在于**同音字、数字/单位、专名、中英混说（code-switching）**。缓解手段按性价比：热词表 → 后处理正则（数字/单位归一）→ 用 MT 模型的上下文知识纠错 → 换 ASR 模型。

## 4. TTS / 配音选型

| 方案 | 参数 | 显存 | 语种 | 能力 | 许可 |
|---|---|---|---|---|---|
| `IndexTeam/IndexTTS-2.5` | ~0.8B | **~6GB** | 中英日西阿 | 零样本音色克隆、情绪向量、语速控制、拼音/CMU/假名发音控制 | bilibili 自定义许可（**非 Apache，商用需逐条核对**） |
| `Index-Echo-S2ST-9B`（端到端） | 9B 解码器 + 生成组件 | **约 22GB（单卡）** | 6 方向：中→英/西/日，英→中/西/日 | 直接语音→语音 + 源说话人音色条件 | Apache-2.0 |
| `FunAudioLLM/Fun-CosyVoice3-0.5B` | 0.5B | 低 | 多语 | Index-Echo 内部用的生成器；RAS 采样 | Apache-2.0（核对） |
| `SWivid/F5-TTS` | — | 低 | 多语 | 强音色克隆、非自回归、快 | MIT（核对） |
| `GPT-SoVITS` | — | 低 | 中英日 | 少样本克隆，社区生态好 | MIT |
| `fluxions-ai/vui`（Vui Nano） | 219M 激活 | CPU 可 | 英语为主 | 流式、可 CPU、无依赖 C 构建 | Apache-2.0 |

**配音流程（离线，直接沿用 `index-dub` 思路）**：

```
mp4 → ffmpeg 抽 16k 单声道 → demucs 人声/伴奏分离 → Silero-VAD 切句（≤9.5s，带时间戳）
    → 逐句 MT（+ 术语表）→ TTS（音色来自源说话人参考片段）
    → 时间轴对齐（双向变速，限幅；过长用 Index-Homura 预先压缩音节）
    → 混音（伴奏回填 + AI 生成标识音轨元数据）→ 封装（视频流 copy）
```

**已知坑（官方 README 自己列的，务必抄进你的文档）**：
- 语速差异大时会被变速/截断，短句会被"放慢填充"，听起来不自然；
- 单说话人效果最好，多人重叠/强 BGM 依赖人声分离；
- S2ST 单句服务端上限约 10.5s，必须 VAD 切句。

**实时配音的硬账**：TTS 0.5~2s/句 + ASR 0.5s + MT 0.2s ≈ 2~5s/句 → 只能做"延迟配音"；且 8GB 卡上 TTS 与 MT 不能同时常驻。

## 5. 路由模型（JEV）与"分模型翻译"的验证方案

### 5.1 JEV 怎么接

```bash
# 服务端（vLLM + System 1 决策接口）
bash JEV-9B/vl/serve.sh          # 视觉版；文本决策用 serve_decide.py
# 调用
POST http://localhost:8000/v1/decide
{"kind":"choice",
 "state":["最近 90 秒字幕文本……", "关键帧：", {"image":"data:image/jpeg;base64,..."}],
 "question":"这段视频属于哪一类内容？",
 "options":["科技数码","影视剧","游戏","学术讲座","动漫番剧","财经商业","生活方式","体育赛事"]}
→ {"options":[...], "probabilities":[...]}
```

要点：
- **选项要带一行"什么时候用"的描述**，官方实测这样最好（CLINC150：仅名称 89.5% → 带描述 93.8%）；问题措辞、JSON/纯文本格式影响不大。
- 一次决策 163ms（JEV-9B）/239ms（JEV-27B-VL），一分钟一次完全无压力。
- **视觉不是必须**，但 `JEV-27B-VL` 仅凭封面做零样本判断 AUC 0.727，说明关键帧对"内容域判定"有增量价值（+0.078 AUC vs 只用标题）。

### 5.2 显存现实

| 运行方式 | 显存 | 说明 |
|---|---|---|
| JEV-9B bf16 | ~18GB | 本地不可行 |
| JEV-9B Q4 GGUF（社区量化） | ~5.5GB | 与 ASR 勉强共存，与 TTS 冲突 |
| JEV-27B(-VL) | 更大 | 只能云端 |
| 先不上 JEV：用现有 MT 2B/ASR 文本 + prompt 分类 | ~0 | **P3 第一阶段就该这么做，先埋点收数据** |

### 5.3 "哪个模型更适合哪类视频"的 A/B 方案（P3 的核心交付物）

1. **建评测集**：8~10 个领域 × 每个领域 80~150 句（从真实视频 ASR 结果里抽，带人工参照译文）。
   - 科技数码 / 影视剧 / 游戏 / 学术 / 动漫 / 财经 / 生活 / 体育 …
   - 覆盖专名、缩写、数字单位、口语、梗（B 站特有表达，Index-Translate 的 MEME 维度正对这块）。
2. **参赛者**：Index-Translate-2B / 9B / 35B(API)、Hy-MT2-1.8B / 7B / 30B-A3B、TranslateGemma-4B/12B、通用 LLM 基线。
3. **指标**：COMET-22 / XCOMET-XXL（自动）+ 人工 5 分制（每领域抽 50 条，双盲）；附带术语命中率、数字/单位正确率、长度偏差。
4. **结论形式**：产出 `routing_table.json`——每个领域 → 排序后的 (模型, 术语表, prompt, 期望延迟/显存)。**路由表是数据产物，不是代码里的 if-else。**
5. **回归**：每次换模型/改 prompt 都跑同一套集，避免"感觉变好了"。

预期结论形态（假设，需验证）：科技/学术类，"术语表 + 领域 prompt"带来的提升 > "换模型"；动漫/社区类，Index-Translate 的 MEME 维度优势可能真实存在；影视剧类，文风与上下文一致性权重更高（修正 pass + NativeLong 有用）。
