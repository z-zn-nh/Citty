# 17 · 评测集成本实测：为什么"先用视频建评测集"这条路线不值

> 起因：P3-a 的领域埋点用的是一台**关键词计数器**（见 [16](16-P3a路由埋点.md)），
> 要证明它准不准，直觉上是"抓一批真实视频、拿 B 站分区当标签算混淆矩阵"。
> 这篇是**先把这条路的成本实测出来**的结果 —— 结论是：**这条路不该走**，理由不是"太贵"，
> 而是"贵且验证的是错的东西"。
>
> 复现：`python tools\probe_bili_meta.py --n 8`（工具：`tools/probe_bili_meta.py`）

## 一、实测数字（本机，2026-10-09）

| 环节 | 实测 | 说明 |
|---|---|---|
| 取一批真实视频 + 全部元数据 | **0.26s / 8 条** | `x/web-interface/popular?ps=20` 一次请求就返回 bvid / **分区 tname** / cid / 时长 / 标题 / UP主 / 播放量 |
| 单条视频的"标签" | **0 秒** | 分区随手就来了 —— **标签根本不是瓶颈** |
| 字幕表查询 | **0.20~0.25s / 条**（两个端点各一次） | `x/player/wbi/v2` 与 `x/player/v2` 都试 |
| **匿名态字幕覆盖率** | **0 / 8** | 两个端点都返回 `code=0 OK` 但 `subtitles: []` —— 不是报错，是**空** |
| 搜索接口 | **HTTP 412 风控** | `bilisearch` 直接 412；第一次调用还超时 31.2s。所以采样只能走 popular/ranking |
| 下载音频 + 转 16k 单声道 | ≈ 4 分钟 / 小时视频 | **估计值**（按 62 分钟长测音频 113.5MB 的经验；本次未重测） |
| 本地 ASR（SenseVoice int8，8 线程 CPU） | **78s / 小时音频** | 实测 RTF 0.021（docs/13）× 3600s |

**汇总**：

- **路线 A（只要标签）**：100 条 ≈ **10 秒**。分区是免费附赠的。
- **路线 B（标签 + 字幕语料）**：**匿名拿不到**（0/8）。要有登录态（`SESSDATA`）；拿到后 100 条 ≈ 1 分钟。
- **路线 C（标签 + 音频 + 本地 ASR 兜底）**：1 小时视频 ≈ 5.2 分钟 → **100 条 ≈ 8.7 小时机器时间 + ~11GB 下载**。

**结论：当前一把可用的云端 LLM 都没有。** 所以任何依赖"LLM 当裁判/当翻译"的方案今天都跑不起来
（`config.yaml` 里指向 DeepSeek 的 `mt.openai_compat` 必然 401）。

> 排错提示：`python-dotenv` **是装好的**，`.env` 能正常加载（5 把 key 都进 `os.environ`）。
> 如果你自己写探针看到"key 不存在"，先检查是不是在 `load_config()` 之前就读了环境变量 ——
> `.env` 是在 `load_config()` 里加载的（我这次就踩了自己的这个坑）。

## 三、为什么这条路线不值（真正的理由）

1. **它验证的东西和目标无关**。分区标签能告诉你"分类器准不准"，但**回答不了"这段该用哪个翻译模型"**。
   一个 100% 准确的"视频类型分类器"，仍然是"用视频级弱代理去猜句级决策"。
2. **8.7 小时换来的是错变量的标签**。这 8.7 小时几乎全花在音频上，而分区标签本身是免费的 ——
   也就是说：**昂贵的部分和有用的部分没有交集**。
3. **有现成语料被忽略了**：仓库里 `out/longrun.srt` 已经躺着 **994 条真实长测句子**（其中 751 条英文原文，
   来自 62 分钟真实视频）。做"翻译质量对比"根本不需要再采数据 —— 现在就能跑。

## 四、换掉被测量的变量（P3-a′）

**不再标"这是什么类型的视频"，改标"这段哪个模型更好"** —— 标签由自动裁判免费产生。

三个部件：

1. **A/B 双后端**：每段同时跑两个 MT。第二个后端用**本地 CPU GGUF**
   （Hy-MT2-1.8B 1.37GB 或 Index-Translate-2B Q4 1.22GB，体积见 [12](12-可本地部署模型清单.md)）：
   零 key、零云端、零显存占用 —— 这是当前唯一可行的第二条腿（云端 key 全不可用，见第二节）。
2. **自动裁判（零 key）**：回译 chrF。
   - 原 ASR 文本 `S`（英文）→ A 出 `T_A`（中）、B 出 `T_B`（中）
   - 用**同一个**回译器（免费 `bilibili_free` 的 zh→en，实测 574ms）把 `T_A`/`T_B` 各自译回英文 → `S_A`/`S_B`
   - 比 `chrF(S, S_A)` 与 `chrF(S, S_B)`，高者胜
   - 同一个回译器消除了"回译器偏好"，只留噪声；噪声水平可以用"同一句重复多次"估出来
3. **记录的变量换成句级可测特征**：token 数、术语率（数字/单位/大写缩写）、专名率、
   口语标记（uh / hmm / you know）、标点密度、是否含代码或公式。
   这些特征**逐句可得、免费、且与"哪个模型更好"直接相关** —— 这才是该喂给路由器的输入。

| | 旧：视频类型 + 真实评测集 | 新：自动裁判，跑在自己看的视频上 |
|---|---|---|
| 人工标注 | 0（分区现成） | 0 |
| 语料采集 | 8.7 小时（音频路线），或需要你给 `SESSDATA` | **0**（用 `out/longrun.srt` 的 994 条 + 平时的流量） |
| 需要的新东西 | 100 个视频的音频 | **1 个 1.2~1.4GB 的本地 MT 模型** |
| 能回答的问题 | "这是数码区还是美食区" | "**这段该用哪个模型**" |
| 验证的对象 | 分类器准确率（与目标无关） | 直接就是路由决策的正确率 |

## 五、立即可执行的顺序（含时间）

1. 下第二个 MT（1.2~1.4GB 本地 GGUF）+ 在 `MTBackend` 里加一档 → **半天**。
2. 回译 chrF 裁判 + 句特征提取，**先拿 `out/longrun.srt` 的 994 条离线跑**（不用等任何新数据）→ **半天**。
3. 把 `citty routes` 报表升级成"胜率 × 句特征"的 arena 报表 → **半天**。

第 2 步做完就能回答第一个真问题：**同一个模型在不同句子特征上的胜率有没有系统性差异** ——
有，路由才值得做；没有，就直接砍掉 P3-b，别浪费后面的时间。
