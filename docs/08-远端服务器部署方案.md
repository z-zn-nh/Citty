# 远端服务器部署方案：把推理搬到云上，本地只留"采集 + 字幕"

> 体检 2026-10-06。本文所有网络数字都是**本机实测**（TCP 握手计时、HTTP 往返），
> 所有模型体积来自 **HuggingFace 元数据接口**（仓库真实字节数）。
> GPU 租用价格区间**未能在本机联网核实**（这台机器连 github.com 都超时），标注为"量级参考，以官网为准"。
> **没有任何模型被下载到本地。**

---

## 0. 结论：可以，而且是三种走法里最合身的一种

对你这台机器（C 盘只剩 18.9GB、当前可用内存 11GB、8GB 显存、又不想往本地拉权重）来说，
**"远端服务器 + 本地调用"恰好绕开了你所有的硬约束**：

| 你的约束 | 远端服务器怎么解决 |
|---|---|
| C 盘只剩 18.9GB | 模型全在服务器，本地**新增磁盘 0** |
| 显存只有 8GB，放不下 ASR+MT+TTS+路由 | 租 24GB 的卡，**四个模型可以同时常驻**，甚至 JEV-9B（17.2GB）也放得下 |
| 内存只剩 11GB | 本地只剩"采集 + 渲染"，内存增量 <200MB |
| 不想下载模型 | 下载发生在服务器上，你本地一个字节都不占 |
| 云端 API 要额度/计量 | 自己的服务器，**没有调用计费**，想跑多久跑多久 |

**而且代价比想象小**：多出来的只有**一次网络往返（实测国内机房 20~60ms）**。

## 1. 三种架构，选哪个

### 方案 A · 服务器只当"模型后端"（**零代码改动，今天就能做**）

```
本地：loopback 采集 → VAD 切句 ──HTTP上传一段音频(≈160KB)──► 服务器：whisper.cpp / llama.cpp
      ◄────────── 识别+翻译结果 ──────────────────────────┘
      字幕窗渲染
```

服务器上把 ASR / MT 起成 **OpenAI 兼容 API**，本地 `config.yaml` 只改 `base_url`。
✅ 这一点**已经被验证过**：上一轮我用本地 mock 服务当 base_url，整套引擎一次跑通
（8 段语音 → 7 句翻译，0 报错）。所以"指到远端"和"指到本地"对代码来说是同一件事。

- 适合：ASR + MT（也就是 P1 的全部内容）
- 代价：每个切句要多传一次音频（160KB）+ 一个 RTT
- 代码改动：**0 行**

### 方案 B · 整个引擎搬到服务器，本地只剩"耳朵和眼睛"（**最优架构**）

```
本地：WASAPI 采集系统声 ──WebSocket 推 PCM──► 服务器：切句 + ASR + MT(+TTS)
      字幕窗 ◄──────── WebSocket 推字幕(几百字节) ────────┘
```

- 好处：以后加配音、加多语种、加 JEV 路由，**全部只动服务器**；本地永远不升级
- 代价：要写一个"音频转发客户端"（预估 ~150 行；本地采集与字幕窗已经现成，WS 协议也验证过）
- 风险：**服务器一断，字幕就停**（方案 A 断网时还能切回云端 key）

### 方案 C · 纯 CPU 云服务器（最省钱，不租显卡）

SenseVoice-Small 只有 **234M 参数、GGUF q8 仅 0.24GB**，且是**非自回归**结构，
天生适合 CPU。一台 **4C8G 的 VPS（约 ¥60~120/月量级）** 跑 ASR，
翻译继续用**免费的哔哩哔哩 API**（本来就不需要 key）。

- 好处：不用租 GPU，成本固定且低
- 风险：CPU 上的 RTF **必须实测**（我预估 0.2~0.5，但不实测不敢下结论）
- 一句话：**这是"没有 key、也不想租卡"时最实际的答案**

## 2. 网络到底够不够（本机实测）

ICMP 被网络屏蔽，所以改用 **TCP 443 握手计时**（真实往返，比 ping 更有参考价值）：

| 目标 | 实测握手 RTT |
|---|---|
| 百度（国内基线） | avg **27.5 ms**（min 24.3） |
| 华为云镜像 | avg **56.0 ms**（min 42.3） |
| AutoDL | avg **58.4 ms**（min 50.2） |
| 哔哩哔哩 API（现用翻译） | avg **60.0 ms**（min 50.7） |
| 阿里云镜像 | avg **64.2 ms**（min **16.3**） |
| 硅基流动 API（现用 ASR） | avg **64.3 ms**（min 38.9） |
| 腾讯云镜像 | avg **87.1 ms**（min 51.1） |
| GitHub（海外） | **直接超时** |

**读法**：国内机房到你这台机器的往返在 **20~60ms** 这一档（最接近的节点甚至只有 16ms）；
而海外目标在这条线路上**连不上**——所以**服务器必须选境内**（上海/北京/广州/杭州）。

### 带宽账本（这是决定性的好消息）

| 项目 | 数值 |
|---|---|
| 16kHz 单声道 16bit PCM | 32 KB/秒 |
| 一个 5 秒切句 | **160 KB** |
| 需要的持续上行 | **0.26 Mbps** |
| base64 之后再 +33% | 0.35 Mbps |
| 国内家宽常见上行 | 30~50 Mbps（千兆套餐） |

→ **上行从来不是瓶颈，余量超过 100 倍。** 唯一的成本就是那次 RTT。

### 延迟对比（本地 vs 云端 vs 远端）

| 环节 | 现在（云端 API） | 远端服务器（境内） |
|---|---|---|
| 音频上传 | 15s 音频 2.1MB，走公网 HTTP | 5s 切句 160KB，多 1 个 RTT |
| 网络增量 | 含在 0.9s ASR 里 | **+20~60ms** |
| ASR 推理 | 平台侧（我们用 1.7B） | 你的服务器（可上更大模型） |
| 翻译 | 平台侧 0.8~2.1s | 你的服务器（1.8B/7B，可控） |

**结论**：远端服务器相比现状，**延迟基本持平甚至更好**（因为服务器上可以选更小的 MT 模型，
而且省掉了免费公网 API 的排队与波动）。真正的收益是"可控 + 无计量 + 大模型随便用"。

## 4. 安全与合规（这一步做错会真出事）

**唯一推荐的暴露方式：什么都不暴露。**

服务器上所有推理服务**只监听 127.0.0.1**，本地用 **SSH 隧道**访问：

```powershell
# 本地执行：把服务器的 8001(ASR) / 8002(MT) 映射到本地同号端口
ssh -N -L 8001:127.0.0.1:8001 -L 8002:127.0.0.1:8002 user@SERVER_IP
```

这样一次性解决四件事：
1. **不需要开放任何公网端口** → 不会被扫、不会被白嫖 GPU
2. **不需要 ICP 备案**（境内服务器用 80/443 + 域名才需要）
3. **自带加密与身份认证**（SSH 密钥）
4. 本地 `config.yaml` 里直接写 `http://127.0.0.1:8001/v1`，**看起来就像本地服务**

> 如果你确实想直接暴露端口：至少加 `--api-key` 鉴权 + 防火墙白名单 + 别用 80/443。
> 裸奔的 llama.cpp 端口在一周内一定会被扫描器找到。

## 6. 远端特有的坑

| 坑 | 说明 | 对策 |
|---|---|---|
| **选错地区** | 海外线路在这台机器上**直接超时**（github.com 实测不通） | 服务器选境内（沪/京/穗） |
| 备案 | 境内机器用 80/443 + 域名需 ICP 备案 | 用 SSH 隧道，或非标端口 + IP 直连 |
| 端口裸奔 | 推理端口被扫到会被盗用 | 只监听 127.0.0.1 + SSH 隧道 |
| 断网即失效 | 本地网络一抖，字幕就停 | 保留云端 key 作降级；方案 A 可以一键切回 |
| 模型下载慢 | 服务器拉 HF 也慢 | 服务器上用 `HF_ENDPOINT=https://hf-mirror.com` 或 ModelScope 源（第三方镜像，自行判断） |
| 忘记关机 | 按量实例 24/7 开着很贵 | 设自动关机策略；用 `bootstrap.sh --stop-after` |
| 显存被自己占满 | 同时常驻太多模型 | 24G 卡上建议 ASR 1.7B + MT 7B 上限，TTS 按需加载 |
| 许可 | 同上（IndexTTS 非 Apache） | 商用前逐条核对 |

## 8. P2（配音）为什么比 P1 更适合放远端

### 8.1 关键区别：P2-a 是**离线批处理**，对延迟完全免疫

P1 是实时的，每个 RTT 都直接加在字幕延迟上，所以远端只能取"低延迟地区"。
P2-a 是"给一个视频文件，几十分钟后拿到配音视频"——**延迟多少不影响任何验收指标**，
验收看的是"处理时长倍率 ≤ 1.5×"和"同步偏差 P95 ≤ 300ms"，两个都是**机器算力**问题。
所以 P2 的重活（音色克隆 TTS、人声分离）**扔到任何地方的 GPU 上都行**，越便宜越好。

### 8.2 拆法：本机管"视频进出"，远端管"模型算力"

```
本机（必须有视频文件）                          远端（只要有 GPU）
  ① ffmpeg 抽 16k 单声道  ──上传 ~38MB──►  ④ 切句 + ASR + MT + TTS（音色克隆）
  ② 原始音轨留着做伴奏                       ⑤ 按时长变速对齐，导出配音人声
  ⑥ 回填混音 + 封装(copy 视频流)  ◄─下载 ~58MB─┘
  ⑦ 写 AI 标识 + 导出 SRT
```

**为什么这么切**（这是设计要点，不是随手分的）：

| 数据 | 体积 | 说明 |
|---|---|---|
| 20 分钟 1080p 原视频 | ≈ 750MB | **绝不上传**，封装用 `-c:v copy` 原地完成 |
| 20 分钟 16k 单声道 WAV | **38MB** | 上传这个（32KB/s × 1200s） |
| 20 分钟 24k 配音人声 | **58MB** | 下载这个 |
| 单集总流量 | **≈ 96MB** | 上行 38MB，普通家宽几分钟 |

伴奏（instrumental）**不上传**：人声分离在本机做（demucs htdemucs 只要 0.16GB，CPU 离线够用，
见 [12](12-可本地部署模型清单.md)），远端只回传"配音人声"，本机拿它和伴奏混。这样下行从
200MB 压到 58MB，而且原音轨一个字节都不用离开本机（**版权角度也更干净**）。

### 8.3 代码改动量

`citty/tts.py` 已有的 `TTSBackend` 适配器加一个 `RemoteTTS`（走 HTTP，跟 ASR 的
`openai_compat` 是同一套写法），配音管线本身留在本机、完全不动。远端只要起一个
"文本进、音频出"的服务 —— 和 `deploy/server/asr_openai_server.py` 同构，可以直接改一个出来。

### 8.4 选远端机器时的两个陷阱

1. **Azure 标准型号没有 GPU**。B/D/E 系列是纯 CPU，GPU 要 NC/ND/NV 系列（T4/A10/V100），
   而且**大概率需要单独申请配额**（新订阅默认 0），这一步常常才是真正的卡点。
   纯 CPU 的 Azure 机器仍然有用（SenseVoice、Hy-MT2-1.8B、demucs、Kokoro 都能跑），
   但**音色克隆（IndexTTS/CosyVoice2）在它上面没意义**。
2. **云电脑关机可能重置系统盘**。5GB 权重别放系统盘 —— 要么挂数据盘，要么写一个
   一键 bootstrap 脚本（`deploy/server/bootstrap.sh` 已是这个模式），下次开机重跑。

### 8.5 先测再定：`deploy/probe_remote.py`

零依赖（只用标准库），新机器直接跑，输出 CPU/内存/磁盘/GPU/显存/**CUDA 是否真可用**/
已装包/到 PyPI·HF·魔搭·GitHub 的连通性/CPU 基准，最后给一行"这台能跑哪些 P2 组件"的结论。

```bash
python3 probe_remote.py          # 人类可读
python3 probe_remote.py --json   # 贴回来看这个
```

> 注意结论里的显存判断**同时看 torch 能不能用 CUDA**：本机就是活教材 ——
> RTX 4060 8GB 显存看着够跑 IndexTTS，实际 torch 是 `2.12.0+cpu`、`cuda.is_available()==False`，
> 只看显存会得到"✅ 能跑"的假结论。
