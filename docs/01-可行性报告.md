# 实时视频翻译插件 · 可行性报告

> 版本：v0.1（调研基线 2026-10-06）
> 目标机器：Windows / i7-12850HX / 32GB RAM / **RTX 4060 Laptop 8GB VRAM**
> 结论口径：技术可行性 + 工程工程量 + 与你四个阶段的对应关系

---

## 0. 一句话结论

**四个阶段全部可做，但"实时"的边界和你设想的不一样：**

| 阶段 | 内容 | 可行性 | 关键结论 |
|---|---|---|---|
| P1 | 实时字幕（中↔英 + 双语字幕） | **高（2~4 周出 MVP）** | 技术全都有现成开源件；难点是音频捕获/同步/字幕渲染这类工程，不是模型 |
| P2 | TTS 接管原声 | **离线配音高可行；实时配音中风险** | 端到端 S2ST 单卡要 ~22GB，你的 8GB 卡跑不了；必须换成 ASR+MT+TTS 串联，且实时只能做"延迟 3~8s 的影子配音" |
| P3 | JEV 判断视频类型 → 分模型翻译 | **可行，但收益必须 A/B 验证** | JEV 的 System 1（一次前向、带校准概率的"选择题"）天生适合做路由；但 JEV-9B/27B 与 8GB 显存冲突，建议走 API 或按需加载 |
| P4 | 拓宽语种 | **无阻塞，纯工程量** | 文本翻译已经有 150 语种；真正卡脖子的是 TTS 语种覆盖、字幕排版（RTL/CJK/断行）和评测 |

**最大的约束不是模型，是 8GB 显存**：ASR + 翻译 + TTS + 路由模型 **不可能同时常驻**。整套架构必须按"常驻小模型 + 按需换入大模型 + 可切换云端 API"来设计（详见 `03-架构设计.md` 第 4 节显存账本）。

三件事你调研时的记忆需要修正：

1. **哔哩哔哩那套是 `bilibili/Index-Translate`**（2026-09-30 发布），不是一个单模型，而是一整个家族：`Index-Translate`（文本，150 语种，2B/9B/35B-A3B）、`Index-Echo`（**S2TT 语音→字幕、S2ST 语音→配音**）、`Index-Homura`（按目标音节数改写译文）、`Index-NativeLong`（长文档）。而且官方还有个 **免费公网 API**（OpenAI 兼容）。这套东西和你的 P1/P2 几乎是一一对应的。
2. **腾讯的是 `Hy-MT2`**（2026-05-21 开源，1.8B / 7B / 30B-A3B，33 语种，Apache-2.0），不是 2025 年的 Hunyuan-MT-7B。官方确实强调"domain-specific（垂直领域）"评测，但**"更擅长科技类"这个判断目前只是假设**，需要用你自己的语料 A/B 验证（见 `02` 第 5 节）。
3. **JEV（autotrust/JEV-\*）不是翻译模型，是"决策模型"**（System 1 类型化决策：是/否、2~256 选 1、0~5 打分，输出**校准过的概率**，一次前向 ~0.16~0.24s），还有带视觉的 `JEV-27B-VL`。它的正确用法是当**分类器/路由器**——正好是你要的"判断视频类型"，但别指望它做翻译。

## 1. 需求拆解

你的四个阶段拆成工程模块：

```
P1  音频 → [捕获] → [VAD 分句] → [ASR] → [MT] → [字幕渲染/导出]     单语/双语/仅译文
P2  音频 → P1 的链路 → [人声分离] → [TTS 音色克隆/端到端 S2ST] → [时间轴对齐] → [混音回放/替换音轨]
P3  视频流 → [采样文本+关键帧] → [JEV System1 域分类] → [模型/术语表/prompt 路由] → 回灌 P1/P2
P4  语言矩阵：ASR 语种 × MT 语种 × TTS 语种 × 字幕排版
```

关键点：**P2/P3/P4 都是 P1 的增量，不是重写。** 因此 P1 的接口设计（可插拔的 ASR/MT/TTS/Router adapter + 统一的 segment 数据结构 + 统一时间轴）决定了后面三个阶段是做加法还是做重写。建议第一版就把 adapter 层留出来，哪怕只有一个实现。

## 2. 现状调研（截至 2026-10-06，来源见 `research/README.md`）

### 2.1 哔哩哔哩：Index-Translate 家族

来源：<https://github.com/bilibili/Index-Translate>（Apache-2.0）、<https://huggingface.co/IndexTeam>

| 组件 | 干什么 | 对你哪一阶段有用 | 事实要点 |
|---|---|---|---|
| Index-Translate 2B/9B/35B-A3B | 文本翻译，150 语种，支持术语表/格式硬约束、文风软约束 | P1、P4 | 官方评测里含 **"字幕翻译"维度**；9B 在自家表上优于 Hy-MT2-7B（FLORES 0.8789 vs 0.8747，WMT26 75.35 vs 60.51，instTrans/MEME 也全面领先——**注意是自评**） |
| Index-Echo S2TT | 语音→带时间戳双语文幕 | P1（中文源） | **仅中文源**，目标 en/ja/es；窗口式（`--max-win 60`，历史 `--ctx-k 5`），2B bf16 约 10GB 显存、A100 上仅 1.4~1.7× 实时 → **不是低延迟流式** |
| Index-Echo S2ST | 语音→语音配音（保留说话人音色） | P2 | 6 个方向（中→英/西/日，英→中/西/日）；单句上限约 10.5s；**配套服务单卡约 22GB 显存** |
| Index-Homura | 按目标音节数改写译文 | P2（对口型/时长对齐） | SandGlass 上 81.92% 输出偏差 ≤10%；官方也说音节控制只是近似 |
| Index-NativeLong | 超长文档翻译，固定模板中↔英、中↔日 | P1（长视频整篇一致性） | 解决人名/术语跨段一致 |
| video-dub 管线 | mp4 → 提取音频 → 人声分离(demucs) → VAD 切句 → 逐句 S2ST → 时间轴对齐 → 输出配音 mp4 | **P2 的参考实现，直接抄流程** | 变速对齐有上限 `--max-stretch`，越界截断；多人重叠/强 BGM 依赖人声分离 |
| extension（LLM Page Translator） | MV3 浏览器扩展翻网页 | P1 前端的参考骨架 | 目录即插件、无构建步骤；已知局限：不支持流式输出 |
| 免费公网 API | `https://index-translate.bilibili.com/v1`（OpenAI 兼容，35B-A3B） | P1 的**兜底/高质量档** | 免费、无需本地 GPU；但**没有 SLA，限流规则未公开**，必须可切换 |

> 重要判断：**Index-Echo S2TT 不适合做实时字幕主力**（窗口 60s、2B 就吃 10GB、A100 上不可实时）。它适合做"**离线高质量字幕批处理**"和"**中文源 → 英/日/西**"的场景。实时链路应该走 **流式 ASR + 文本 MT** 的级联方案。

### 2.2 腾讯：Hy-MT2

来源：<https://huggingface.co/tencent/Hy-MT2-7B>（Apache-2.0）、<https://github.com/Tencent-Hunyuan/Hy-MT2>

- 三档：**1.8B / 7B / 30B-A3B(MoE)**，33 语种（含藏/维/蒙/哈等民族语），2026-05-21 开源。
- 全档位有 **GGUF**（含 2bit、1.25bit 极端量化，1.8B 可压到 **440MB**）和 FP8，适合本地/端侧。
- 官方定位："fast-thinking"、覆盖 general / real-world business / **domain-specific** / instruction-following 四类评测；同时开源了 `IFMTBench`，并且是 **WMT26 视频字幕翻译任务**的赞助方之一。
- 遗留信息：上一代 `Hunyuan-MT-7B` + `Hunyuan-MT-Chimera-7B`（2025-09，33 语言，WMT25 31 项里拿 30 个第一，Chimera 是**多译文集成**模型）。

**对你 P3 的意义**：Chimera 那种"多模型草稿 + 集成"的思路，是"分模型翻译再融合"的成熟做法，可以参考。但"科技类更适合腾讯"目前**没有可引用的证据**，需要自建评测（见 `02` 第 5 节）。

### 2.3 JEV（autotrust）：决策模型，不是翻译模型

来源：<https://huggingface.co/autotrust/JEV-9B>、`JEV-27B`、`JEV-27B-VL`、`GEV-26B-Decide`（均 Apache-2.0）

| 事实 | 数值 |
|---|---|
| System 1 能力 | 类型化决策：yes/no、**2~256 选 1**、0~5 打分；输出每个选项的**校准概率**，**一次前向**出结果 |
| 延迟 | JEV-9B ≈ **163ms/决策**；JEV-27B-VL ≈ **239ms/决策**；GEV-26B-Decide ≈ 61ms |
| 接口 | `POST /v1/decide`（vLLM + `serve_decide.py`），`{kind, state, question, options}` |
| 视觉能力 | `JEV-9B`（2026-10-03 起支持图像）、`JEV-27B-VL`：截图/封面进，动作概率出；零样本短视频推荐（仅凭封面）AUC **0.727**，追平协同过滤 |
| 长上下文 | 支持 256K token prompt；在 250K 文本里找一句话做判断，20/20 正确 |
| 无训练扩展 | CLINC150 全 150 意图当选项：仅意图名 89.5%，带一行描述 93.8% |

**结论**：拿 JEV 做"这条视频属于哪个领域 → 用哪个翻译模型/术语表"完全对症，而且它的"概率 + 选项"形式很适合做**带置信度门控的路由**（低置信度就回退默认模型）。但注意：
- 9B/27B 规模在 8GB 卡上无法与 ASR/MT/TTS 共存（bf16 远超显存），得走 GGUF 量化、按需加载或云端 API；
- JEV 的 System 1 是"**快判断**"，不是"深度理解"，分类粒度建议 8~16 类，别做上百类细粒度。

## 3. 关键技术路径的可行性判断

### 3.1 音频捕获
- **桌面（推荐主路径）**：WASAPI loopback 直接抓系统输出，不需要虚拟声卡；只用于 TTS 回放时才需要虚拟声卡（VB-CABLE）。
- **浏览器扩展**：MV3 的 `tabCapture` 只能抓标签页（正合适 B 站/YouTube 网页），抓不到本地播放器/B 站客户端。
- **DRM 内容**（Netflix 等）**抓不到音频**，属于硬边界，UI 上要明确提示。
- 采样：16kHz 单声道喂 ASR；TTS 回放 22.05k/24k，独立回调线程。**风险低。**

### 3.2 实时字幕链路（P1 的核心）
级联链路（VAD + 流式 ASR + MT）与端到端（Index-Echo S2TT）对比：

| | 级联（推荐） | 端到端 S2TT |
|---|---|---|
| 语言方向 | 任意（ASR 语种 × MT 语种） | 目前仅 中→英/日/西 |
| 延迟 | 可控，0.4~1.5s 上屏（chunk 320ms 档） | 窗口式 60s，非低延迟 |
| 显存 | ASR 0.6B + MT 1.8/2B ≈ 4~5GB | 2B 包 bf16 就 ~10GB，A100 上 1.4~1.7× 实时 |
| 可维护性 | 每个环节可替换、可观测 | 黑盒，出错难定位 |
| 质量 | 靠 MT 质量（已足够好）+ 上下文修正 | 语音上下文化，术语一致性略好 |

**结论**：P1 走级联；端到端 S2TT 作为"离线高质量导出"或"中→英/日/西 的 v2 增强"，不做实时主力。

**延迟预算（目标：本地链路端到端 ≤1.5s，云端 MT 容忍 ≤2.5s）**

| 环节 | 预算 | 说明 |
|---|---|---|
| 捕获缓冲 | 20~50ms | WASAPI loopback 小缓冲 |
| VAD + 分块 | 320~560ms | nemotron 320ms chunk 起步，静音段用 VAD 提前 commit |
| ASR 计算 | 30~100ms | 0.6B 流式，GPU 上远快于实时 |
| 断句/稳定策略 | 0~400ms | LocalAgreement/AlignAtt：用"稳定前缀"抢先上屏，尾字后补 |
| MT（本地 1.8~2B） | 80~250ms | 单句 20~40 token 输出，首 token 优先 |
| 渲染上屏 | 16~50ms | 透明置顶窗 / content script overlay |
| **合计** | **≈0.7~1.5s** | 云端 MT 则 +150~600ms RTT |

再加一个 **"修正 pass"**：句子 commit 后 1~3s 内，用带前后文（前 3~5 句）和术语表的重译覆盖字幕。这一步几乎不增加感知延迟，但质量提升明显——**这是"实时字幕"和"实时+后修正"的分界线，强烈建议第一版就做**。

### 3.3 TTS 接管原声（P2）
必须分成两种产品形态，否则需求会互相打架：

| 形态 | 触发场景 | 做法 | 可行性 |
|---|---|---|---|
| **A. 离线/准离线配音** | 用户主动"把这条视频配成中文"、VOD、下载后的片子 | 走 `index-dub` 同款流程：demucs 人声分离 → VAD 切句（≤9.5s）→ 逐句 S2ST 或 ASR+MT+TTS → 变速对齐 → 替换音轨，BGM 回填 | **高**（现成流程可抄；只是 8GB 卡跑不动 22GB 的 S2ST 服务，需改用 ASR+MT+IndexTTS-2.5 串联，或云 GPU） |
| **B. 实时接管（边播边配）** | 直播、追剧、无字幕生肉 | 缓冲 3~8s 后连续播出，播放器侧用倍速/延迟对齐；TTS 逐句生成 | **中**。物理下限：ASR 0.5s + MT 0.2s + TTS 0.5~2s + 对齐 ≈ **2~5s/句**，因此只能做"延迟配音"；且 8GB 卡上 TTS（~6GB）与 MT 抢显存，必须串行化（换入换出 2~5s，不可接受）→ 建议 **TTS 独占、MT 走 API** 的组合 |

**结论**：P2 先做 A（价值明确、风险低），再做 B 的"实验特性"。别承诺"零延迟同声传译"。

配音的两个硬问题：
1. **时长对齐**：中→英通常变长，`index-dub` 用双向变速（限幅）解决，Index-Homura 用音节控制从源头控制长度。两者结合最好。
2. **原声怎么办**：实时模式建议原声降 -12dB 保留（保住 BGM 和音效），比实时人声分离靠谱；离线模式再上 demucs。

### 3.4 JEV 路由（P3）
可行的落地形态：

```
每 30~60s 或检测到话题切换时：
  聚合最近 60~120s 的 ASR 文本（截断 2~4K tokens）+ 1~3 张关键帧/封面
  → POST /v1/decide  (kind=choice, options=[科技, 影视, 游戏, 学术, 番剧, 财经, 生活, ...])
  → {domain, probability}
  → 置信度 ≥ τ 才切换：{model_id, glossary, genre_prompt, style}
```

- 分类是**慢变量**：一分钟判断一次就够，不需要每句都判断，成本可忽略（JEV-9B 163ms）。
- 用**概率门控**（τ≈0.6）+ 迟滞（连续 2 次一致才切换），避免"模型来回横跳"。
- 路由价值来源有三块，**按性价比排序**：① 术语表（几乎零成本，收益最直接）② 领域 prompt/文风软约束 ③ 换模型（收益需要证明）。
- 8GB 显存问题：JEV-9B bf16 ≈ 18GB，本地只能 GGUF Q4（~5.5GB）按需加载，或走云端；替代方案是先用 **1.8~2B 级小模型 + prompt 分类**，把 JEV 留给离线批量/VOD 场景或云 GPU。**这一条要写进架构取舍，别默认 JEV 常驻。**

### 3.5 多语种扩展（P4）
- MT 侧不是瓶颈（Index-Translate 150 语种；Hy-MT2 33；TranslateGemma 55）。
- 真正的瓶颈：
  - **ASR 语种覆盖**（nemotron 36 locale / Whisper 99 / VibeVoice 10；中文强项是 FunASR）；
  - **TTS 语种覆盖**（IndexTTS-2.5 只有中英日西阿 5 种；端到端 S2ST 只有 6 个方向）→ 想配 20 种语言的音，需要引入 CosyVoice3/F5-TTS 等多语 TTS 或云端 TTS；
  - **字幕排版**：RTL（阿拉伯/希伯来）双向文本、泰文无空格断行、CJK 行内断行规则、字体 fallback；
  - **质量与评测**：低资源语种必须有可回归的评测集，否则"支持了"只是能跑。
- 工程量：**每个语种（含排版+评测）约 2~5 天**，目标 10 语种 ≈ 4~8 周。

## 4. 本地硬件约束（最重要的一节）

RTX 4060 Laptop **8GB** 是整套方案的物理天花板。粗算常驻显存：

| 组件 | 显存估计 | 备注 |
|---|---|---|
| CUDA context + 运行时开销 | 0.5~0.8GB | 每个进程单独一份 |
| 流式 ASR 0.6B（fp16） | ~1.3GB | nemotron 0.6B；Whisper large-v3-turbo int8 ≈ 1.5~2GB |
| MT 1.8B/2B（FP8/INT8） | ~2.0~2.6GB | 含 KV cache；GGUF Q4 更低 |
| MT 9B（FP8） | ~9~10GB | **本地不可行** |
| TTS IndexTTS-2.5 0.8B | **~6GB** | 官方口径；自回归 + flow-matching 解码 |
| JEV-9B（bf16） | ~18GB | **本地不可行**，只能 Q4 GGUF（~5.5GB）或云端 |
| S2ST 一体化服务 | ~22GB | 官方口径，**本地不可行** |

**因此的架构结论（写死的三条）**：

1. **常驻集合 = 流式 ASR(0.6B) + MT(1.8/2B)**，约 4~5GB，实时字幕的稳态。
2. **TTS 是"独占式"组件**：走独立进程，用时才加载（换入 2~5s）→ 离线配音场景无所谓，实时场景要提前预热；实时配音时 **MT 必须切到云端 API** 才能腾出显存。
3. **"高质量档"（9B/35B/27B-VL/S2ST）全部走云端或离线批处理**：哔哩哔哩的免费 35B API、你自建的云 GPU、或夜间批量任务。**"本地全模型路由"在这台机器上是不成立的**，报告里必须显式告诉用户"档位差异"。

## 5. 工程量与工期（单人全职口径）

| 阶段 | MVP | 可用稳定版 | 主要工作 |
|---|---|---|---|
| P1 实时字幕 | **2~3 周** | 4~6 周 | 音频捕获、流式 ASR 接入、断句与修正 pass、字幕渲染三模式、SRT 导出、同步/暂停/seek/倍速处理 |
| P2 离线配音 | 2~3 周（抄 index-dub 流程） | +2 周 | 人声分离、S2ST/TTS 接入、时间轴对齐、混音、AI 标识 |
| P2 实时配音（实验） | +3~5 周 | 视质量 | 缓冲策略、延迟对齐、TTS 预热、断流恢复 |
| P3 JEV 路由 | 1~2 周 | +1~2 周评测集 | decide 接口接入、域标签设计、路由策略与迟滞、A/B 评测集 |
| P4 多语种 | 10 语种 4~8 周 | — | 语种矩阵、字体/RTL 排版、按语种术语表、评测 |

**建议的推进顺序**：P1 → P3 的路由**埋点**（先只记录域标签，不改行为）→ P2 离线配音 → P4 扩语种 → P2 实时配音（实验）→ P3 真正生效。

理由：P3 的收益依赖 P1 跑出来的真实数据；先把埋点做上，跑两周自然得到"哪类视频更适合哪个模型"的证据，避免拍脑袋。

## 6. 风险登记（Top 10）

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| 1 | 8GB 显存无法同时容纳 ASR+MT+TTS+路由 | **高** | 常驻小模型 + 云端兜底 + 模型按需换入；UI 明示档位 |
| 2 | 实时与质量的矛盾（快字幕不准、准字幕不快） | **高** | 双阶段：稳定前缀抢先上屏 + 修正 pass 覆盖 |
| 3 | 端到端 S2ST 本地跑不动（22GB） | 高 | 改用 ASR+MT+IndexTTS-2.5 串联；或云 GPU / 离线批处理 |
| 4 | 实时配音延迟 3~8s，体验与预期不符 | 中高 | 明确定位为"延迟配音"，不承诺同传；提供原声 ducking 模式 |
| 5 | 免费 API 无 SLA / 限流 / 模型下架 | 中 | adapter 化，至少 2 个可用后端（本地 + 云）一键切换 |
| 6 | 版权与平台条款（抓流、再分发配音视频） | 中高 | 默认仅本地显示、不落盘、不自动上传；导出功能做使用提示 |
| 7 | 深度合成合规（AI 配音必须标识、声音权） | **高（法律）** | 输出音视频叠加"AI 生成"标识；音色克隆需本人同意（IndexTTS-2.5 许可也这么要求）；不提供真人声音克隆模板库 |
| 8 | DRM 内容无法捕获音频 | 中 | UI 明确提示，不尝试绕过 |
| 9 | 多说话人/重叠语音/强 BGM 导致 ASR 崩坏 | 中 | VAD + 说话人分离；离线用 demucs；实时接受降级 |
| 10 | 模型许可差异（IndexTTS-2.5 是 bilibili 自定义许可，非 Apache） | 中 | 商用前逐模型核对条款，见 `04` 第 4 节 |

## 7. 明确建议：先别做的三件事

1. **别一开始就做"实时配音"**——它的延迟下限是 2~5s/句，8GB 卡还要和 MT 抢显存，投入产出比最差，放最后。
2. **别一开始就做"多模型路由"**——没有评测集的路由就是随机数。先把 P1 跑起来 + 采集域标签和翻译质量数据，再决定路由规则。
3. **别自己写 ASR/TTS/MT**，也别自建流式框架——`WhisperLiveKit`（11.1k★）已经把流式 ASR + 同传 + 说话人分离 + WebSocket 接口做完了；你的工作量应该花在**音频捕获、字幕渲染、时间轴同步、模型路由、以及 B 站场景适配**上。

---

## 8. 结论

- **整体可行**：四个阶段都有成熟开源件支撑，没有技术死路。
- **P1 是唯一必须自己啃的部分**（音频捕获 + 同步 + 渲染 + 修正 pass），也是全部价值的地基，2~3 周能出能用的 MVP。
- **P2/P3/P4 是"配置与集成"为主的工作**，前提是 P1 的 adapter 层和统一 segment 结构一开始就留对。
- **真正的三条硬约束**：8GB 显存、实时配音的物理延迟、AI 配音的合规标识。这三条决定了产品要"分档"，而不是"一键全自动"。
